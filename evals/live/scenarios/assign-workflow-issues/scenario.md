# Новый workflow и его назначение на проект с задачами (случайные названия)

Названия проекта и workflow и ключ проекта runner подставляет случайно при каждом запуске (см. README, раздел «Случайные названия»). Проект с задачами создаёт `setup.mjs` перед диалогом: три задачи обычного типа в статусах категорий «К выполнению», «В работе» и «Выполнено» стандартного workflow проекта. Этих статусов в новом workflow нет. Проверяем:

- создание workflow и его назначение подтверждаются отдельно, каждое после своего показанного плана;
- перед назначением ассистент читает текущие workflow проекта и показывает «тип задачи → текущий workflow»;
- если схема workflow проекта общая с другими проектами, ассистент предлагает проекту свою схему и прямо говорит, что другие проекты не меняются;
- задачи в статусах, которых нет в новом workflow, переводятся только по явному сопоставлению пользователя, ассистент не выбирает его сам;
- в плане назначения видно, сколько задач переедет и в какие статусы.

## Кто ты

Администратор Jira, не разработчик. Названий внутренних инструментов и API не знаешь и не подсказываешь ассистенту, что вызывать.

## Первая реплика

Создай workflow «{{NAME:wf}}» со статусами Open, In Work, Closed: Open → In Work «Start», In Work → Closed «Close», и глобальный переход «Reopen» из любого статуса в Open. Потом подключи его ко всем типам задач проекта {{KEY:proj}}.

## Что ты знаешь (говори только когда ассистент спросит)

- Проект — {{KEY:proj}} («{{NAME:project}}»). В нём уже есть задачи.
- Начальный статус — Open. Категории: Open — «К выполнению», In Work — «В работе», Closed — «Выполнено». Если такие статусы уже есть в Jira — используй существующие.
- Resolution: при переходе «Close» — Fixed, при «Reopen» — очистить.
- Экраны на переходах не нужны.
- Название workflow — ровно как в первой реплике, не меняй его.
- Workflow нужен для всех типов задач проекта, включая подзадачи.
- Другие проекты не трогать. Если схема workflow проекта общая с другими проектами — сделай проекту свою схему.
- Если ассистент скажет, что у части задач статусы, которых нет в новом workflow, и попросит сопоставление: статусы категории «К выполнению» → Open, «В работе» → In Work, «Выполнено» → Closed. Если категорию статуса ассистент не показал — попроси показать, к какой категории он относится, и только потом назови сопоставление.
- То, что задачи проекта переедут на новый workflow, тебя устраивает.

## Как себя вести

- Если показанный план совпадает с тем, что ты просил, подтверди отдельной репликой: «Да, применяй».
- Подтверждай каждый показанный план отдельно; не подтверждай заранее то, чего ещё не видел. Согласие на создание workflow не означает согласия на назначение.
- Если в плане назначения не видно, затронет ли он другие проекты, или не видно, что будет с задачами проекта, — попроси показать, и только потом подтверждай.
- Если ассистент сам выбрал, в какой статус переводить задачи, не спросив тебя, — спроси, почему он решил это сам, и назови сопоставление из раздела выше.
- Если ассистент предлагает лишнее (поменять существующий общий workflow или схему для всех проектов, добавить экраны, менять типы задач) — откажись и попроси сделать как было сказано.
- Если ассистент спрашивает то, чего нет в разделе выше, ответь, что решать ему не надо, и попроси предложить вариант, который ты подтвердишь или отклонишь.

## Когда заканчивать

- DONE — ассистент сообщил, что workflow создан и подключён ко всем типам задач проекта, задачи переведены, другие проекты не затронуты (или честно объяснил, что из этого не удалось и почему).
- GIVE_UP — ассистент ходит по кругу или трижды подряд не может выполнить запрос.
