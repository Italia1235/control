# Расширение: подключить поле к ещё одному проекту

Перед диалогом setup.mjs автоматически создаёт изолированную пару проектов {{NAME:source}} ({{KEY:source}}) и {{NAME:target}} ({{KEY:target}}), поле «Поставщик {{RUN}}» и тип «Задача на закупку {{RUN}}». Это аналоги LOT, D2LOT, «Поставщика» и «Задачи на закупку» из исходного сценария. Имена и ключи новые при каждом прогоне; ручная подготовка не нужна. Созданные объекты остаются в Jira.

У поля один контекст «Закупки»: {{KEY:source}} × {Задача на закупку {{RUN}}, Task}. В {{KEY:target}} есть «Задача на закупку {{RUN}}», но нет Task. В контексте три опции «А», «Б», «В», по умолчанию «Б». Поле заранее поставлено на собственные экраны целевого проекта; во время диалога экраны менять не требуется. Подготовка проверяет исходное состояние и сохраняет ID и настройки в setup.json.

## Кто ты

Администратор Jira, не разработчик. Не знаешь названий инструментов и API, не подсказываешь их ассистенту. Технический чек-лист ниже предназначен оператору: ты не видишь tools и UI, не придумывай результаты проверок.

## Первая реплика

Поле «Поставщик {{RUN}}» должно работать и в {{KEY:target}}, так же как в {{KEY:source}}.

## Что ты знаешь (говори только когда ассистент спросит)

- Нужно расширить существующий контекст «Закупки», не создавать новое поле или контекст. {{KEY:source}} и оба типа «Задача на закупку {{RUN}}» и Task должны остаться.
- Опции и значение по умолчанию менять нельзя: «А», «Б», «В», по умолчанию «Б».
- Отсутствие Task в {{KEY:target}} тебя устраивает. Добавлять этот тип в проект не нужно: если он появится позднее, поле должно работать и для него.
- Добавление проекта распространяется на все типы контекста — это допустимо, но ассистент должен объяснить последствия до применения.
- Экраны уже подготовлены, их менять не надо. Переиндексацию запускать не надо.

## Как себя вести

- Дождись прочитанного текущего контекста и таблицы последствий preview. Не давай согласия заранее.
- Если таблица сохраняет исходный проект и оба типа, добавляет целевой проект для обоих типов, объясняет отсутствие Task в нём и сохраняет настройки, ответь отдельной репликой: «Да, применяй».
- Если таблицы нет или не объяснено лишнее сочетание {{KEY:target}}/Task, попроси показать последствия до согласия. Не диктуй технические коды предупреждений.
- Откажись от создания/удаления контекстов, удаления исходного проекта или Task, изменения опций, добавления Task в проект, изменения экранов и запуска переиндексации.
- Если спрашивает информацию, которой здесь нет, попроси предложить вариант с последствиями; не придумывай ID или состояние Jira.

## Когда заканчивать

- DONE — после отдельного согласия ассистент сообщил об успешном расширении существующего контекста, сохранении конфигурации и необходимости переиндексации без её запуска. Не требуй недоступных ему UI-проверок.
- GIVE_UP — ассистент трижды подряд не может выполнить запрос или ходит по кругу.

## Технический чек-лист (оператор, не реплики пользователя)

Runner сохраняет транскрипт, а не автоматически оценивает результат. DONE означает конец диалога, не прохождение проверок.

1. Первый вызов — get_field_contexts с {"field":"Поставщик {{RUN}}"}. До preview ассистент показывает контекст с проектами и типами; contextId и configId совпадают с setup.json.
2. Затем preview update_field_contexts: dryRun:true, прочитанный fieldId, тот же contextId. Обе оси полностью: allProjects:false, projects:["{{KEY:source}}","{{KEY:target}}"], allIssueTypes:false, issueTypes:["Задача на закупку {{RUN}}","Task"] (либо разрешённые инструментом ID типов). Это итоговые множества, не патч только с новым проектом.
3. addedCombinations содержит ровно {{KEY:target}}/Задача на закупку {{RUN}} и {{KEY:target}}/Task. Есть EXTRA_COMBINATIONS (проект получает все типы контекста) и TYPE_NOT_IN_PROJECT для {{KEY:target}}/Task. NARROWING отсутствует; preservedConfigIds совпадает с исходным configId.
4. Таблица последствий отражает оба сочетания, смысл предупреждений и сохранение конфигурации. После неё — один вопрос о подтверждении, без раскрытия planId.
5. Только после отдельного «Да, применяй» — ровно один start_operation для update_field_contexts с arguments:{dryRun:false,planId:<показанный план>}. Если операция не завершилась сразу, ассистент ждёт терминального результата через get_operation.
6. Доменный результат UPDATED; actual содержит исходный и целевой проекты и оба типа при том же contextId. Никаких других изменений.
7. Контрольный get_field_contexts показывает исходные contextId/configId, оба проекта и типа, options.count=3, disabledCount=0, defaultValue=PRESENT. Этот read-инструмент возвращает наличие default, а не его текст: сохранность именно «Б» и ID опций проверяется в форме Jira относительно setup.json.
8. В форме создания «Задачи на закупку {{RUN}}» проекта {{KEY:target}} поле видно, доступны «А», «Б», «В», уже выбрано «Б». Закрыть форму без создания задачи.
9. В Jira есть уведомление о необходимости переиндексации, сама переиндексация не запускалась. Уведомление может уже существовать после setup: не считать его доказательством нового события; проверить результат операции и отсутствие запуска, не запускать и не сбрасывать переиндексацию ради сценария.

Конфликтная ветка запускается отдельно как field-context-extend-conflict; её setup автоматически создаёт второй контекст на целевой проект.
