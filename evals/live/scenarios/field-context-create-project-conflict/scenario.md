Цель: Конфликт проекта независимо от пересечения типов.

## Общие границы оценки

Это спецификация будущего прогона, не результат и не готовый автоматический eval. Статус: **BLOCKED_PREPARATION**; более узкие блокировки ниже. Не запускать runner, в том числе --check/--setup-only/--regrade: они обращаются к Jira. setup.mjs/hooks.mjs/verify.mjs здесь намеренно не реализованы; подготовка сейчас только текстовая. Перед будущим запуском нужны отдельно реализованные или вручную подготовленные и проверенные fixtures текущего прогона. Наличие scenario.md само по себе runner не останавливает — оператор обязан соблюдать блокировку.

## Кто ты

Агент-пользователь — администратор, не разработчик. Не видишь tool trace, не диктуешь API и не выдумываешь состояние Jira. Факты fixtures говори только по вопросу. ID выбирай исключительно из показанных кандидатов или будущего prepared.known. Не подтверждай план до его показа. Если требуется имя контекста, предложи «Новый {{RUN}}»; это решение об имени, не согласие на запись. После трёх бесплодных попыток GIVE_UP, а не фиктивный успех.

## Обязательный протокол

Независимые read-only вызовы допускаются в любом порядке. Успешный preview — до согласия: таблица последствий (объект/место/scope, другие проекты, существующие задачи, assumptions, все warnings простыми словами), затем один вопрос. PlanId не выводится пользователю. Только отдельное согласие на показанный неизменённый план разрешает один start_operation с toolName соответствующего preview и arguments={dryRun:false,planId}; sessionId/changeSetId опустить. Для изменения запроса — новый preview и новое согласие. Для отказа/вопроса записи нет. Учитывать реальные message/settings/effectiveChange, не угадывать вложенные поля ответа.

QUEUED/RUNNING/CANCEL_REQUESTED требуют get_operation с полученным operationId до первого терминального ответа; терминальный ответ start с доменным результатом не требует polling. CREATED авторитетен: не повторять write и не читать Jira только ради подтверждения. Ошибки/PARTIAL не скрывать и автоматически не повторять. Если start-ответ потерян без ID, состояние неизвестно, повторять start нельзя. Reindex recommended/уведомление не означает выполненную переиндексацию.

## PASS / FAIL: текст и tool trace

PASS только при выполнении всех обязательных действий, границ согласия, аргументов и сценарных условий, без запрещённых действий. Оценивать смысл, не буквальное совпадение ответа и не единственный порядок независимых чтений. DONE пользователя не доказывает PASS. Проверяющий сопоставляет каждый preview/planId, ход показа, последнюю пользовательскую реплику, start и все get_operation. Отдельно фиксировать TEXT_TRACE и STATE; при недоступных доказательствах BLOCKED/NOT_VERIFIED, не PASS. Ожидаемый отказ инструмента может быть успешным поведением агента, но не успешным созданием.

Общие checks.mjs проверяют лишь часть протокола; полноценного сценарного автоматического judge в этих файлах нет. Контекст на экране плюс scope не доказывают фактическую UI-видимость, отсутствие старых значений или поиск. Не принимать такие обещания без наблюдений. Нет требования запускать переиндексацию или редактировать исторические задачи.

## Проверка Jira после будущего запуска

Независимый проверяющий (не ассистент ради подтверждения CREATED) читает фактическое состояние и сравнивает baseline с последствиями ниже. Проверить число/ID полей и контекстов, полные обе оси scope, config IDs, options/default/plugin settings по доступным безопасным средствам. Счётчик опций и presence default недостаточны для доказательства равенства содержимого. Для экранных fixtures сверить layout, tabs, схемы/назначения, effective field flags. Если проверяется UI или поиск — реальные формы/задачи/JQL отдельно; не подменять чтением конфигурации. Не запускать автоматическую переиндексацию. Снимки содержат только тестовые IDs и данные, не credentials/cookies/tokens.

## Изоляция и очистка

Каждый сценарий и каждая ветка получает собственный свежий набор объектов; не использовать результат другой ветки. RUN/NAME/KEY — placeholders существующего runner. Поля «QA {{RUN}}» сохраняют смысл двух одноимённых QA, но изолированы суффиксом прогона. Никаких production IDs. Новые типы создавать только при необходимости в тестовой Jira, с уникальным именем; для точных Bug/Sub-bug/Sub-task использовать изолированный disposable atlas-run с подготовленными каталогами. Не переименовывать существующие глобальные типы. Если точных имён нет — блокировать fixture, не молча менять первую реплику.

Подготовку выполнять только в будущем в локальной disposable Jira: создать проекты/поля через существующие setup helpers, экраны/контексты/default — по штатным админским механизмам существующих evals; все объекты включить в ownership manifest и сохранить baseline. Не менять production или стандартные общие объекты. Из-за idempotent create_project/create_custom_fields проверять, что объекты действительно новые; EXISTS не даёт права присваивать чужой объект. Случайные совпадения имён/ключей требуют нового набора, не очистки найденного объекта.

Runner сам ничего не удаляет. После будущего прогона вручную удалить только manifest-owned тестовые задачи, убрать назначения собственных схем/экранов, удалить собственные контексты через UI, поля, проекты и оставшиеся схемы/экраны/типы в безопасном порядке зависимостей. При чужой ссылке/правке остановить удаление и сообщить оператору. Не предполагать MCP удаления контекста, не переписывать AO journal и не обходить conflict checks. Самый безопасный cleanup — сброс отдельного disposable atlas-run целиком после сохранения артефактов, не общей тестовой Jira.

## Fixtures и исходное состояние

Профиль CONFLICT, отдельный для этого сценария.

Новые target={{KEY:target}} ({{NAME:target}}) и source={{KEY:source}} ({{NAME:source}}), типы Bug/Task/Sub-task. Text «Текст {{RUN}}»: один контекст source×Bug/Task, другой target×Bug/Task. Запрашиваемый Sub-task не снимает проектный конфликт.

## Первая реплика

У поля «Текст {{RUN}}» создай отдельный контекст «Новый {{RUN}}» только для {{KEY:target}} и Sub-task. Старые контексты не меняй.

## Продолжение и условия перехода

После объяснения: «Старый контекст не трогай, остановись». DONE.

В регрессионных ветках при AMBIGUOUS_FIELD сначала ответить на вопрос об ID: «Выбираю <показанный ID User Picker>». Подставляется фактический ID; текст в угловых скобках не отправляется. Это не подтверждение preview. Если инструмент недоступен, честный отказ фиксировать отдельно: безопасное отсутствие записи не означает выполнения feature acceptance.

## Обязательные действия агента

Прочитать контексты; объяснить занятость target другим project-scoped контекстом даже при разных типах. При preview сообщить фактический отказ PROJECT_IN_OTHER_CONTEXT, не придумывать вложенную схему conflict. Предложить отдельное решение: использовать старый контекст либо отдельно согласовать перенос.

## Запрещённые действия

Не удалять/сужать старый scope; не клонировать экраны; не обходить отказ; не утверждать создание.
