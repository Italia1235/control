# Required comment L5 — deterministic online screen writer integration smoke

Uses the existing live runner's setup/hooks/verifier and `--regrade`; NO second runner, NO model call needed for verification. All fixture preparation and writes happen through ordinary Control MCP preview -> consequences table -> real human yes -> start_operation -> terminal get_operation. Automatic setup apply is forbidden. Read-only setup validates fresh isolated workflow provenance, real IDs, no foreign consumers, no draft and existing foreign-view/no-screen fixture actions. If those optional legacy fixtures cannot be obtained by permitted means, BLOCKED rather than UI/XML/REST mutation bypass.

## Первая реплика

На согласованном изолированном тестовом workflow выполни проверку записи экранов: создание с экраном, добавление перехода с экраном, SET, замена другим экраном и CLEAR; чужой view и переход без экрана не меняй. Для каждой записи сначала отдельный preview, таблица последствий и моё подтверждение. Ничего не применяй автоматически.

## Deterministic operator sequence

1. Capture approved `configure_workflow` with `create` (and no `existing`) on a SEPARATE fresh `createdWorkflow`: one transition (with unique `key`) whose `screen` is the actual id and another explicitly requested transition WITHOUT screen (no `screen` and no screen SET in `transitionRules`). Terminal status CREATED. Export resulting XML (`create-with-screen`, actual returned createActionId): screen transition has meta=id plus view=fieldscreen; no-screen transition has neither. The main workflow is a permitted copy carrying a legacy foreign view; configure_workflow create cannot fabricate that fixture. This creation trace is included in the saved verification trace with unambiguous seq/turn numbering; source approval transcript is retained. Both workflows are isolated LOCAL-005- objects with zero consumers.
2. ADD_TRANSITION with screen SET through `configure_workflow` (`existing:{workflow,version:"ACTIVE",expectedRevision,changes:[{op:"ADD_TRANSITION",name,source,targetStepId,screen:{action:"SET",screenId}}]}`, no transitionRules/newScreens) (`add-with-screen`, actual returned addActionId) adds one action, leaves every old action/attribute/rule untouched. Existing target actionId is separate from addActionId so ADD cannot overwrite a preexisting transition.
3. Through configure_workflow.existing.changes: UPDATE_TRANSITION actionId screen SET first screen (`set`), SET different second real screen (`replace`), CLEAR (`clear`). Each before/after XML snapshot has both metadata and view checked, and the remainder of the entire graph compared structurally. Each update preview targets only the stated screen operation. Require UPDATED_INACTIVE and durable WORKFLOW_SAVE APPLIED/MATCH. Metadata-only false positives are failures.
4. CLEAR on otherViewActionId (`other-view-clear`) removes screen meta but retains its non-fieldscreen view. noScreenActionId and all foreign attributes/rules remain intact from baseline through all steps. Do not create this fixture with a new raw XML mutation.
5. Last captured saved XML must equal current Jira XML structurally; arbitrary disconnected fixture pairs cannot prove online smoke. Do not compare full XML strings: jira.updated.date metadata can legitimately change.
