# field-context-create-select-options

Цель: новый контекст существующего select-поля со своими опциями и новый контекст существующего текстового поля для другого проекта, без нового поля и без правки старых контекстов. Изолированный аналог D2LOT / «Система» / «Серийный номер».

## Кто ты

Ты администратор Jira, не разработчик. Tool trace не видишь, API не диктуешь, состояние Jira не выдумываешь. Говоришь коротко и по-русски. Не подтверждаешь план, пока его не показали целиком. Факты ниже сообщаешь только по вопросу.

## Что ты знаешь

- Проект {{KEY:target}} ({{NAME:target}}), тип задачи Bug. Соседний проект {{KEY:source}} ({{NAME:source}}).
- Поле «Система {{RUN}}» (выпадающий список) уже используется в проекте {{KEY:source}} со своими значениями. Там всё должно остаться как есть.
- Поле «Серийный номер {{RUN}}» (текст) тоже уже есть и используется в {{KEY:source}}.
- Для {{KEY:target}} в «Системе» нужны ровно три значения в таком порядке: «Заря R&D», «Заря-С», «Зарница R&D». Значение по умолчанию не нужно.
- Если спросят имя контекста: «{{KEY:target}} Bug».
- Экраны и обязательность в этом запросе не нужны.

## Первая реплика

В проекте {{KEY:target}} для Bug нужны поля «Система {{RUN}}» со значениями Заря R&D, Заря-С, Зарница R&D и «Серийный номер {{RUN}}». Поля уже есть в Jira, новые не создавай, в {{KEY:source}} ничего не меняй.

## Продолжение и условия перехода

- На вопрос отвечай фактами выше.
- Если предлагают создать новое поле, переименовать поле или добавить {{KEY:target}} в контекст {{KEY:source}}: «Нет, нужен отдельный контекст существующего поля для {{KEY:target}}».
- Когда показан план, где для «Системы» видны ровно три нужных значения в нужном порядке и {{KEY:target}} × Bug для обоих полей: «Да, применяй».
- DONE после итогового результата обеих записей. Если ассистент сообщает отказ или PARTIAL, не выдавай это за успех: DONE с фиксацией. После трёх бесплодных попыток GIVE_UP.

## Обязательные действия агента

get_field_contexts для обоих полей; create_field_context с dryRun=true для каждого поля: «Система» — projects=[{{KEY:target}}], issueTypes=[Bug], options=[Заря R&D, Заря-С, Зарница R&D]; «Серийный номер» — тот же scope без options. Одна таблица последствий для обоих превью (scope, опции, неизменные старые контексты, предупреждения) и один вопрос. После «да» — по одному start_operation на каждый planId.

## Запрещённые действия

create_custom_fields, update_field_contexts, правки экранов/обязательности, повторный apply. Не копировать опции старого контекста, не придумывать другие значения, не обещать значение по умолчанию.

## Проверяемые последствия

verify.mjs: у «Системы» ровно два контекста; новый — {{KEY:target}} × Bug с собственной конфигурацией и опциями ровно «Заря R&D, Заря-С, Зарница R&D» в этом порядке без default; старый контекст с прежними config/опциями/scope. У «Серийного номера» новый контекст {{KEY:target}} × Bug, старый без изменений. По одному apply create_field_context на поле, только dryRun/planId; запрещённых записей нет.
